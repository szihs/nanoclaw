### Verify-then-review-before-report rule (hermes-builder only)

Apply whenever an implementation produces a draft PR (or patch) in the fork.

- **Order is fixed:** `hermes-tester` first → `hermes-reviewer` only with the tester's PASS `[Test Report]` attached → the terminal `[Fix Report]` to parent only after `[Review Verdict] APPROVE`. Never request review before a PASS report exists for the current head, never report up before APPROVE, and never fold test/review state into a bare `[Report]`.
- **Tester round 1 is an UNMARKED fresh delegation on the tester's edge.** The tester has never written to you on this thread, so there is no inbound to reply to, and the always-on chain-routing gate denies any marker-prefixed send that lacks `in_reply_to`: `send_message(to="hermes-tester", thread_id="hermes-<req-id>", text="Fix report — <fork-slug>#<N>: <title>\n…")` — first line must not begin with `[`; `thread_id` = the canonical thread you were dispatched on, propagated unchanged. Body: fork draft-PR URL + head SHA, plugin dir + key, ADR path, acceptance-test path and local result, `hermes plugins doctor --ci` result, the `scripts/run_tests.sh` chunks you ran. Then `send_file` the ADR with the same `thread_id`. The tester runs the hermetic suite T1–T12, the UI tier and the desktop tier in its own container — you do not run them.
- **Tester round 2 answers `[Test Report] FAIL` as a reply** (`in_reply_to=<test-report-msg-id>`) whose first line is `[Fix Report] <fork-slug>#<N> (test round 2, head <sha>): …` — the only `[Fix Report]` that is not the terminal one; it carries a new head for re-verification, not a result. Fix exactly the failing rows first, push the new head, then send. Max **2** `[Test Report] FAIL` per PR: after the second the tester escalates to the orchestrator itself — send no third hand-off; report `blocked: verification not converged` on the spec edge (unmarked, last report re-attached) and stop.
- **Reviewer round 1 is an UNMARKED fresh delegation on the reviewer's edge**, sent only once a PASS `[Test Report]` for the current head is in your inbox: `send_message(to="hermes-reviewer", thread_id="hermes-<req-id>", text="Fix review request — <fork-slug>#<N>: <title>\n…")` + `send_file` of the ADR and of the tester's `test-report-<sha7>.md` verbatim (never pasted or summarised). The reviewer audits the report + the diff, re-runs nothing, and spot-checks at most one command. `[Fix Review Request]` is used ONLY when answering `[Review Verdict] REQUEST_CHANGES` as a reply (`in_reply_to=<verdict-msg-id>`). This is additional to the `CODE_REVIEW` codex critique, not a substitute.
- **A new head always re-enters the tester.** Any push after a `[Test Report]` invalidates it; the reviewer binds to the head SHA the report names and bounces a stale one. `REQUEST_CHANGES` → fix in the same worktree, push, re-run doctor + tests, hand off to the tester again (reply to its last `[Test Report]`), then re-request review with the new PASS report attached. Max **2** review rounds; a third `REQUEST_CHANGES` → terminal `[Fix Report]` with `blocked: review not converged` listing the open findings, and escalate.
- **After dispatching, end the turn.** Do not poll. No meta-acks to the tester or the reviewer; only substantive replies (a re-request after changes, or an answer to a question the verdict asks).
- **The terminal `[Fix Report]` is a reply on your parent edge** (`in_reply_to=<the inbound that delegated this requirement>`), carrying the tester's verdict line (test round, `DESKTOP=…` incl. any `install_packages` request verbatim), the reviewer's verdict line verbatim, the PR URL, and the doctor/test results. Never send it to the reviewer or the tester.
- **You never merge and never mark ready.** `gh pr merge` in any form (`--squash`, `--merge`, `--rebase`, `--auto`, `--admin`), `gh pr ready`, `gh api -X PUT /repos/.../pulls/<N>/merge`, and pushing your branch onto `$BASE` are all forbidden to you — **the Orchestrator is the sole merge authority** and also flips the draft when it merges. You hold the fork's write credentials, which is exactly why this line is here and not only in the workflow body: your last writes to the fork are the final `git push` on the plugin branch and the PR-description refresh. The merge notice and the ledger's `merged`/`blocked` column are the Orchestrator's. If it comes back with `blocked: P<n>` (relayed down the spec edge), answer with the missing evidence or a new head — never by merging, re-targeting, or un-drafting the PR yourself.
- **Only legitimate skips:** `hermes-tester` not in your destinations → request review without a report and say so (the reviewer requests the run itself); `hermes-reviewer` not in your destinations → state that in the terminal `[Fix Report]`. Patch-only mode, "trivial change", and time pressure are not skips.
