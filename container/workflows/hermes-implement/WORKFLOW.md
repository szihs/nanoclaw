       cd /workspace/agent/wt-{{target_slug}}
       git push -u origin plugin/{{target_slug}}                                  # origin = the fork; never `upstream`

       **Pointer rules — what you may assert and what you may not.** The gate's three conditions are read off documents you did not write, and the join between them is mechanical:

       | Gate condition | Original the Orchestrator reads, and where | Your job |
       |---|---|---|
       | reviewer APPROVE | the `[Review Verdict]` message in **`hermes-reviewer`'s own session** (`ncl sessions messages`, `cli_scope: global`) — its `## Head SHA`, `## Acceptance criteria`, `## Diff scope`, `## Negative control` sections | name the holding agent, the msg id, the round, the head it binds to |
       | tester PASS at this head | `test-report-<sha7>.md` **as `hermes-tester` sends it** on the orchestrator↔tester edge — its `## Results` table, incl. one `AC-<req-id>-<n>` row per ADR criterion | name the holding agent, the msg id, the filename, the head |
       | e2e-only-or-ADR-cited diff | the reviewer's `## Diff scope` + the **architect's** ADR already in the Orchestrator's inbox from the `[Spec handoff]` | attach your ADR copy + its sha256 so a divergence is detectable; give your `git diff --name-only` as a cross-check, labelled as such |

       So: **forward, never transcribe.** `send_file` the exact inbox paths you received, unedited and unregenerated, and quote the `sha256sum` values so each forwarded copy can be bound to the original. Your ADR copy is the one file here you *could* have edited (you `cp`-ed it in at Setup and you own the directory) — which is exactly why the architect's `[Spec handoff]` attachment, already in the Orchestrator's inbox, is the authoritative one and yours travels only as a hash to compare. Never edit the ADR's `## Acceptance criteria` table: an id you added, dropped or reworded to match the tests you wrote is the single most damaging edit available in this chain, and it is detectable only by that comparison. Do not paste the reviewer's tables or the tester's `## Results` into your message, do not compress a set of row statuses into one word, do not write a per-criterion table of your own — a summary written by the party being gated is exactly the evidence this shape removes. Anything you say about the contents of an original is a convenience note the gate is entitled to ignore.

       **A contradiction is reported, not reconciled.** If your own reading disagrees with an original — the report's head is not your head, an `AC-` row is missing or not `PASS`, the reviewer's `## Diff scope` lists a path your diff does not, `APPROVE` sits next to a `FAIL` row — the report is **not sendable as an APPROVE hand-off**. Do not smooth it over in prose and do not fix it by re-running anything: state `mismatch: <what> — <original says X, I see Y>` in the Blocker bullet, and if it is a stale report or a moved head, go back through Ship step 2 (tester) → step 4 (reviewer) for the current head instead. Missing original (no verdict arrived, no report file, report for another head) → there is nothing to point at: send the unmarked `blocked:` report on the spec edge per step 3, never a `[Fix Report]` with an empty or reconstructed pointer.

       **The head SHA in this report is what gets merged.** Any push after sending it invalidates the report and the tester's PASS: the PR then re-enters Ship step 2 (tester) → step 4 (reviewer) and you send a NEW terminal `[Fix Report]` with the new head. Never touch the branch after this send.

       Afterwards — and only afterwards, since both are file writes that would stale the OUTPUT_REVIEW the marker send needs — refresh the PR description with the final state (append the Test Report's `## Results` table under **How to test**) and append the outcome to `/workspace/agent/fixes/{{target_slug}}.md`. Never send this terminal `[Fix Report]` before APPROVE and never to the reviewer — the only other `[Fix Report]` you ever send is the test-round-2 reply to `hermes-tester` (Ship step 2), which carries a new head for re-verification, not a result. Don't wait for human confirmation to open the draft.

# hermes-implement

## Hermes deltas

- Every capability is a Hermes plugin (`plugin.yaml` `manifest_version: 1` + `__init__.py register(ctx)`, or an Agent Plugins v1 package). Edits outside `plugins/**`, `website/docs/**`, `tests/**` are allowed only under the ADR's `## CORE-CHANGE` citation of `{{vars.release_tree}}/<file>:<line>`; otherwise stop and reply to the architect.
- Fork checkout at `/workspace/agent/hermes-agent`; one worktree per target at `/workspace/agent/wt-<target_slug>`, branched off `origin/release/<tag>-e2e-fixed`; `uv sync --locked --python /usr/bin/python3 --extra dev` in an `Agent` subagent, outside `scripts/run_tests.sh`; never `uv python install`.
- **Base = the pinned e2e baseline branch, derived not hardcoded.** `TAG` from `{{vars.release_tree}}/RELEASE_MANIFEST.json` (fallback `{{vars.release_tag}}`), `BASE="release/${TAG}-e2e-fixed"` — the branch, the worktree, `git diff origin/$BASE...HEAD`, and `gh pr create --base "$BASE"` all use it. Fork `main` mirrors upstream `main`, hundreds of commits past the pin, and is never a valid base. Branch absent on the fork → **STOP**: no worktree, no code, no push, no PR, no silent fallback; log `blocked` and report it unmarked on the spec edge for the Orchestrator (which owns the branch).
- Tests only via `scripts/run_tests.sh`; plugins validated with `.venv/bin/hermes plugins doctor <dir> --ci`; `HERMES_HOME=/workspace/agent/.hermes-testbed` for CLI smoke runs; long runs chunked in `Agent` subagents with explicit Bash `timeout`, never `run_in_background`.
- Draft PR to the fork only (`--base "$BASE"`, `--draft`), then **`hermes-tester` first**: the hand-off is a fresh unmarked message on `thread_id="hermes-<req-id>"` (round 1) or a `[Fix Report]` reply to its `[Test Report] FAIL` (round 2); max 2 FAILs per PR, then the tester escalates and you report `blocked`. Review request to `hermes-reviewer` only with the PASS `[Test Report]` attached verbatim (`[Fix Review Request]` marker only on a reply); a new head always goes back through the tester. `[Fix Report]` to parent only after `[Review Verdict] APPROVE`.
- **The terminal `[Fix Report]` is a POINTER SHEET for the Orchestrator's merge gate, not the evidence.** The gate (reviewer APPROVE + tester PASS at that head SHA + in-surface-or-ADR-cited diff) is decided on the originals, read from their AUTHORS' sessions — the reviewer's `[Review Verdict]` out of `hermes-reviewer`'s session, the tester's canonical `test-report-<sha7>.md` requested from `hermes-tester` — because the builder is the party being gated and may neither attest to its own review nor host the transcript the gate trusts. The report also never reaches the Orchestrator directly (there is no builder↔orchestrator edge): `hermes-architect` copies its locators into the `[Triage Resolution]` that triggers the gate. So the report carries locators, not findings: PR number + URL, full head SHA, base branch (`release/<tag>-e2e-fixed` + manifest tag/commit), canonical thread, the verdict msg id + round + head, the Test Report msg id + inbox path + sha256 + head, the ADR path (its `## Acceptance criteria` ids are the join key), and your `git diff --name-only origin/$BASE...HEAD` labelled as a cross-check. Both files are forwarded verbatim with `send_file`; no retyped reviewer/tester tables, no per-criterion table of your own. A contradiction with an original goes in the Blocker bullet as `mismatch:` — never reconciled in prose. A push after that send invalidates it — new head → tester → reviewer → new terminal report.
- **The builder never merges and never marks ready.** No `gh pr merge`, no `gh pr ready`, no merge API call, no push to `$BASE`. The Orchestrator is the sole merge authority (squash-only, into the baseline branch) and owns the post-merge notice and the ledger's `merged/blocked` column.
